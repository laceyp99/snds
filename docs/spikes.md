# Phase 0 spike results

Evidence behind the pinned decisions from Phase 0 ("Resolve Foundation Spikes") in `plan.md`.
Each section says what was measured, where it was measured, and the decision it supports.

Measurement machine (unless noted): Windows 11 Pro 10.0.26200 VM, 4 physical cores (Intel
family 6 model 151, i7-12700F slice), 15.6 GB RAM, NVIDIA GeForce RTX 3060 12 GB, driver
576.80 (CUDA 12.9 driver API), uv 0.12.6. All test audio is synthetic and generated by the
spike scripts. No user music was read.

Python spike scripts are in `spikes/python/`. Their outputs go to `spikes/output/`, which is
git-ignored. To run any of them after syncing the worker environment:

```powershell
uv sync --project worker --extra cuda --frozen   # or --extra cpu
uv run --project worker --no-sync python spikes/python/<script>.py
```

## Python environment

**Decision.** The worker is a `uv` project in `worker/`, with pinned Python, exact pins and a
committed `worker/uv.lock`. PyTorch is selected through two mutually exclusive extras, `cpu`
and `cuda`.

| Item | Pin | Source |
|---|---|---|
| Python | CPython **3.12.14**, uv-managed (`.python-version`; `requires-python = "==3.12.*"`; `python-preference = "only-managed"`) | uv python downloads |
| torch (extra `cpu`) | **2.11.0+cpu** | `https://download.pytorch.org/whl/cpu` (`explicit = true`) |
| torch (extra `cuda`) | **2.11.0+cu128** | `https://download.pytorch.org/whl/cu128` (`explicit = true`) |
| demucs | **4.1.0** (in both extras) | PyPI (wheel) |
| numpy / scipy | **2.5.3** / **1.18.1** | PyPI |
| soundfile | **0.14.0** (bundles libsndfile **1.2.2** with MP3 read and write) | PyPI |
| resampler | `scipy.signal.resample_poly` (part of scipy) | - |
| BPM | in-house numpy/scipy estimator, so no new dependency (see [BPM analysis](#bpm-analysis)) | - |
| dev group | pytest **9.1.1**, ruff **0.16.9** | PyPI |
| torchaudio | **not installed and not needed**. demucs 4.1.0 no longer imports it, and SNDS does its own I/O with soundfile | - |

Notable transitive pins from `uv.lock`: julius 0.2.8, einops 0.8.2, lameenc 1.8.4,
huggingface-hub 2.0.0, safetensors 0.8.0, sphn 0.2.1, pyyaml 6.0.3, tqdm 4.70.1. The lock has
41 packages. `tool.uv.environments` restricts it to `sys_platform == 'win32' and
platform_machine == 'AMD64'`. Adding Linux later is a one-line change.

**Why the lock is structured this way**

- `torch` and `demucs` appear only in the extras. A bare `uv sync` therefore never
  resolves a third, PyPI-hosted torch build.
- `[tool.uv] conflicts` makes `--extra cpu --extra cuda` a hard error ("Extras `cpu` and `cuda`
  are incompatible with the declared conflicts").
- `uv sync` is an exact sync. Without an extra it **uninstalls torch and demucs**. Scripts must
  always pass exactly one of `--extra cpu` or `--extra cuda` (with `--frozen`). `uv run` is
  inexact and leaves torch alone, but scripts should still use `uv run --no-sync` or call
  `worker\.venv\Scripts\python.exe` directly.
- One venv per machine. The CUDA build also runs on CPU. Switching extras swaps only the torch
  wheel.

**Why torch 2.11.0 and cu128**

- `download.pytorch.org` currently offers cu126 up to 2.14.0, cu128 up to **2.11.0**, cu129 up
  to 2.9.0, and cu130/cu132 builds.
- cu130 and newer need an R580+ driver. This machine's 576.80 driver cannot run them.
- CUDA 12.6 has no Blackwell support, so cu126 builds exclude RTX 50-series GPUs.
- 2.11.0 is therefore the newest torch that covers Turing through Blackwell on an R570+ driver.
  torchaudio also stops at 2.11.0 on both PyPI and PyTorch's index. That is irrelevant here
  because torchaudio is not used.

**`spike-uv-cpu-env` and `verify-spike-clean-machine`: passed.** The test used a copy of
`worker/` in `%TEMP%`, with an empty `UV_CACHE_DIR`, an empty `UV_PYTHON_INSTALL_DIR` and no
`.venv`.

- `uv sync --extra cpu --frozen` downloaded CPython 3.12.14 and 40 packages in **52 s** total.
- `env_probe.py` returned ok: torch 2.11.0+cpu, no CUDA, demucs imports cleanly, libsndfile
  1.2.2 reports MP3.
- `pytest` passed 2 tests. `ruff check` and `ruff format --check` were clean.
- The same sync in the real `worker/` (no venv, warm Python) took 41 s.
- CPU footprint: about 0.7 GB (uv cache and venv share hardlinks) plus 70 MB for Python.

**`spike-uv-cuda-env`: passed.**

- `uv sync --extra cuda --frozen` into the same `worker/.venv` downloaded the 2.6 GiB
  (2,753,189,216 B) wheel and swapped `torch==2.11.0+cpu` for `2.11.0+cu128` in 82 s.
- `torch/` in the venv is 4.1 GB. The venv total is 4.4 GB.
- Disk tip: after syncing, `uv cache clean torch` frees about 4.5 GB. The venv keeps its
  hardlinked copy, but the next switch of extras re-downloads the wheel.
- `env_probe.py` on the 3060:
  - `cuda_available: true`, `torch.version.cuda = 12.8`, cuDNN 9.19 (91900), capability 8.6.
  - `get_arch_list() = sm_75, sm_80, sm_86, sm_90, sm_100, sm_120`.
  - A GPU matmul matches the CPU result within 4.2e-7 relative error.

**CUDA runtime and driver contract**

- The Windows wheel bundles the CUDA 12.8 user-mode runtime in `torch\lib`: cudart64_12,
  cublas/cublasLt 12, cuDNN 9, cuFFT 11, cuSPARSE 12, nvrtc and nvJitLink. Only the NVIDIA
  display driver is needed. No CUDA toolkit is needed, and no global Python or CUDA mutation
  happens.
- Supported GPUs are compute capability 7.5 to 12.0: Turing (GTX 16, RTX 20), Ampere,
  Ada, Hopper and Blackwell (RTX 50).
- Maxwell, Pascal and Volta (GTX 9xx/10xx) are not in the cu128 build. On those GPUs the
  worker's compute probe fails and the job falls back to CPU (see the next table).
- Minimum driver: CUDA 12.8 GA needs Windows **≥ 570.65** (12.8 Update 1: ≥ 572.61), according to
  NVIDIA's CUDA 12.8 release-notes table. NVIDIA lists minor-version compatibility for 12.x as
  driver ≥ 525, but that is untested here. The documented supported floor should be **R570+**.
  The tested driver is 576.80.

**`verify-spike-cuda-fallback`: passed.** `spikes/python/cuda_fallback.py` runs a real
worker-like child per scenario, separating 20 s of synthetic audio with progress messages.

| Scenario | How the failure is caused | Outcome |
|---|---|---|
| A auto | healthy GPU | device `cuda:0`, 4 progress messages, 1.21 s |
| B hidden GPU | `CUDA_VISIBLE_DEVICES=-1` | `cuda_detected=false`, automatic CPU, 8.9 s |
| C bad device | `SNDS_CUDA_DEVICE=cuda:7` makes the probe hit a real `AcceleratorError: CUDA error: invalid device ordinal` | automatic CPU, reason reported |
| D mid-job failure | `SNDS_FAULT_INJECT=cuda_midjob` raises a CUDA error from the progress callback after 2 segments | child exits code 3 with `cuda_failed`; the parent makes an explicit retry in a **new process** with `--device cpu`, which succeeds |
| E force CPU | `--device cpu` with a healthy GPU | CPU, reason "forced by request" |

**Proposed compute policy for the worker**

1. With `auto`, check `torch.cuda.is_available()`, then run a small compute probe on the
   chosen device.
2. If the probe fails, fall back to CPU and report the reason.
3. A CUDA failure after the job has started exits with a dedicated code (3 in the spike).
4. The app then offers an explicit or automatic CPU retry in a fresh worker. It never retries
   inside a process whose CUDA context may be poisoned.

**Acquisition.** `spikes/python/fetch_htdemucs.py` downloads the file and verifies it.

- It streams to `.th.part`, hashes while streaming, and verifies size and SHA-256 against the
  pins before an atomic `os.replace`. A mismatch deletes the partial file.
- It writes `htdemucs.yaml`. A re-run only re-hashes the file (0.07 s).
- The download took 1.6 s here.

**Loading.** The loader is `_common.load_htdemucs`. It never uses torch.hub or the HF cache.

1. Verify size and full SHA-256.
2. Call `torch.load(path, map_location="cpu", weights_only=True)` inside
   `torch.serialization.safe_globals([...])`.
3. Build the model with `demucs.states.load_model(package_dict)`.

The allowlist is exactly what `torch.serialization.get_unsafe_globals_in_checkpoint` reports:
`demucs.htdemucs.HTDemucs`, `fractions.Fraction`, `numpy.core.multiarray.scalar`,
`numpy.dtype` and `numpy.dtypes.Float64DType`. So no arbitrary pickle code runs, even if the
hash check were bypassed.

The upstream path `demucs.pretrained.get_model("htdemucs", repo=<dir>)` also works with 4.1.0
and gives an identical state dict. It uses `weights_only=False` and checks only the 8-hex
filename prefix.

**Demucs version: 4.1.0, not 4.0.1 (deviation, with evidence)**

demucs **4.1.0** was published to PyPI on 2026-07-11 by the original author (homepage
`github.com/adefossez/demucs`). Evidence for choosing it:

- **Bit-identical output.** On torch 2.11.0+cpu, `demucs_version_compare.py` separated a 20 s
  clip with the pinned checkpoint using 4.0.1 (throwaway venv) and 4.1.0 (worker venv).
  `max_abs_diff = 0.0`.
- **4.0.1's stock loader breaks on torch ≥ 2.6.** `get_model(repo=...)` raises
  `UnpicklingError: Weights only load failed`. Our own loader works around this in either
  version.
- **4.0.1 pins torch to ≤ 2.11 forever.** It needs `torchaudio` at import time (via
  `openunmix`), and torchaudio's last release is 2.11.0. It also pulls `dora-search`,
  `omegaconf` and `antlr4-python3-runtime` 4.9.3, which is sdist-only and needs a local build.
  4.0.1 itself is sdist-only too.
- **4.1.0 needs no torchaudio, dora or openunmix.** It vendors the Wiener filter and ships a
  wheel.
- **4.1.0 adds an `apply_model(callback=...)` hook.** It fires on `state: start|end` per
  segment, with `segment_offset`, `shift_idx` and `model_idx_in_bag`. Raising from the
  callback cancels the remaining chunks. That gives the worker real progress and cooperative
  cancellation without tqdm scraping.

Cost of 4.1.0: it pulls huggingface-hub, hf-xet, httpx2, safetensors, sphn and lameenc, which
SNDS does not use at runtime. It is also only about 2.5 months old. Fallback if 4.1.0 regresses:
4.0.1 plus torchaudio 2.11.0 plus our loader works. That path was measured in this spike.

**Proposed separation settings:** `apply_model(model, mix, shifts=0, split=True, overlap=0.25,
device=...)`, using the model's own 7.8 s segment.

- `shifts=1` (the CLI default) pads 0.5 s and applies one `random.randint` offset. With a
  single shift nothing is averaged, so it only makes output non-deterministic.
- `shifts=0` is deterministic and slightly cheaper. It matters for cache stability.
- Pass the mix on CPU and `device="cuda"` so only the segments live in VRAM (peak 550 MiB).

## Stem normalization

**Pipeline prototype** (`spikes/python/normalize_stems.py`, `verify-spike-audio-alignment`):

1. Decode with soundfile (`float32`, `always_2d`).
2. Duplicate mono to 2 channels.
3. Resample `source_sr → 44100` with `resample_poly` at the exact reduced ratio
   (e.g. 48k: 147/160).
4. Run `apply_model` with the settings above.
5. Resample each stem `44100 → source_sr`.
6. **Trim or zero-pad to exactly the decoded source frame count.**
7. Write 4 × stereo **32-bit float WAV** at `source_sr`.
8. Re-open the written files and validate them.

Each case is 10 s plus an odd remainder, so frame counts are not round numbers. Results are
identical on CPU and CUDA to ±0.05 dB.

|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 44k1 stereo PCM16 | 44100 | 2 | 453345 | 453345 | yes | 0 / −0.0003 | 0,0,0 | −33.0 dB | (identity) | −3.0 | −4.2 | −3.3 | 0 |
| 48k stereo PCM24 | 48000 | 2 | 480777 | 441714 | yes | 0 / 0.0002 | 0,0,0 | −32.6 dB | −45.1 dB | −3.0 | −5.3 | −3.5 | 0 |
| 96k stereo float | 96000 | 2 | 960001 | 441001 | yes | 0 / 0.003 | 0,0,0 | −33.4 dB | −42.7 dB | −3.0 | −6.5 | −5.3 | 0 |
| 192k stereo PCM24 | 192000 | 2 | 1920003 | 441001 | yes | 0 / −0.002 | 0,0,0 | −34.2 dB | −44.2 dB | −3.0 | −10.1 | −8.4 | 0 |
| 22.05k stereo PCM16 | 22050 | 2 | 220505 | 441010 | yes | 0 / 0.0001 | 0,0,0 | −37.4 dB | −46.6 dB | −3.0 | −4.8 | −3.2 | 0 |

| 48k mono PCM24 | 48000 | 1 | 480011 | 441011 | yes | 0 / −0.0002 | 0,0,0 | −34.1 dB | −45.0 dB | −3.3 | −5.7 | −4.0 | 0 |

"Contract" means every stem re-opens as `samplerate == source`, `channels == 2`,
`frames == source frames`, with all samples finite. The "≤20k" band is `min(20 kHz, 0.45·fs)`.

How to read the table:

- About −33 dB is htdemucs's own reconstruction error. The sum of stems is not exactly the mix,
  and the 44.1 kHz rows (no resampling) show the same value. Normalization adds nothing
  measurable in-band.
- For sources above 44.1 kHz, content above 22.05 kHz is absent from the stems by
  construction. The full-band residual therefore rises (96k: −13.7 dB; 192k: −12.5 dB).
- Original A/B plays the untouched original, so this band-limit is audible only as a
  difference between Stem Mix and Original.

**Resampler choice: `scipy.signal.resample_poly`**, with the default Kaiser(5.0) window,
zero-phase and output length `ceil(n·up/down)`.

Round trip `fs → 44.1k → fs` without the model:

| fs | scipy lag / sub-sample | scipy ≤20k / ≤16k | julius (`resample_frac`, full=True) lag / sub | julius ≤20k / ≤16k |
|---|---|---|---|---|
| 48000 | 0 / 0.0005 | −45.1 / −63.7 dB | 0 / 0.0 | −46.4 / −72.5 dB |
| 96000 | 0 / 0.008 | −42.7 / −65.7 dB | 0 / 0.0 | −39.6 / −74.4 dB |
| 192000 | 0 / 0.011 | −44.2 / −64.0 dB | 0 / 0.0 | −41.4 / −67.1 dB |
| 22050 (bands 9.9k / 7.9k) | 0 / 0.0 | −46.6 / −62.0 dB | 0 / 0.0 | −51.7 / −70.8 dB |

Both are sample-aligned and both are adequate.

- **Why scipy:** BSD licence; the dependency is already pinned; plain NumPy, so normalization
  is unit-testable without torch; about 25 to 80 ms per 10 s. julius's first call costs 1.3 to
  1.7 s.
- **julius** (MIT, already installed via demucs) has a slightly flatter inner passband. It is
  a drop-in alternative if listening tests prefer it.
- **soxr** (LGPL-2.1) was not needed.

**Proposed `unknown-normalization-tolerance`**, enforced by the worker before cache
finalization:

- Frame count: **exact**. Every stem has `frames == decoded source frames`; the tolerance is 0.
- Format: `samplerate == source samplerate`, `channels == 2`, 32-bit float WAV, all samples
  finite.
- Alignment: the integer cross-correlation lag between the stem sum and the source is **0**
  over the whole file and in 1 s windows at start, middle and end. Sub-sample lag must be
  ≤ 0.05 samples; the measured maximum was 0.003.
- Gross-failure guard: the in-band residual between stem sum and source should be ≤ −10 dB
  (hard fail) and ≤ −20 dB (else warn). Measured values were −32.6 to −37.4 dB. Tune this on
  the rights-cleared fixture.

**Proposed clipping policy**

- The worker writes stems as **IEEE float32 WAV** (soundfile `subtype="FLOAT"`).
- It **never clips, limits or normalizes**.
- It records per-stem and stem-sum peak dBFS in provenance.
- Headroom and limiting belong to the C++ master stage.
- Evidence: a loud, clipped master at −0.1 dBFS produced a drums stem at **+2.0 dBFS** and a
  stem sum at **+0.46 dBFS**. Clipping to PCM would have damaged 323 samples.
- Disk cost of float32 stems: 4 stems × 2 ch × 4 B × fs, which is about **85 MB per minute at
  44.1 kHz** (about 184 MB/min at 96 kHz). The cache UI must show this.

### MP3 decode (input to C++ Original A/B alignment)

`spikes/python/mp3_probe.py` writes fixtures plus `manifest.json` to `spikes/output/mp3/`.
libsndfile 1.2.2 from the soundfile wheel decodes MP3 through its bundled **mpg123**, and
encodes through its bundled **LAME 3.100**. **No FFmpeg is involved.**

| 44k1_stereo_10s.lameenc.mp3 | 441000 | lameenc, CBR 192, **no Xing/LAME tag** | 384 → 442368 | - | 442368 (+1368) | 443030 (estimate) | **1105 late** |
| 44k1_stereo_odd.lameenc.mp3 | 453345 | same | 395 → 455040 | - | 455040 (+1695) | 455720 | 1105 late |
| 48k_stereo_odd.lameenc.mp3 | 480777 | same | 419 → 482688 | - | 482688 (+1911) | 482688 | 1105 late |
| 44k1_mono_odd.lameenc.mp3 | 441003 | same | 384 → 442368 | - | 442368 (+1365) | 442368 | 1105 late |

Findings:

- With a LAME/Xing tag, libsndfile + mpg123 decoding is **gapless and exact**: the original
  length with lag 0.
- Without a tag, the decode contains **576 (encoder delay) + 529 (decoder delay) = 1105 extra
  leading samples**, plus trailing padding.
- `sf.info().frames` is only an estimate for tagless files. The worker must count
  **decoded** frames, and stems must match that decoded count.

What C++ needs to check for Original A/B:

- Decode these fixtures with JUCE's `MP3AudioFormat` and compare against `manifest.json`
  (`sf_decoded_frames`, `mp3_info_tag.encoder_delay`, `mp3_info_tag.padding`,
  `mp3_audio_frames`).
- If JUCE ignores the LAME tag, its original will start about 1105 samples later than the
  stems (about 25 ms, an audible flam in A/B).
- Options:
  - (a) Record `source_decode = {decoder, frames, lame_delay, lame_padding}` in provenance and
    offset or trim the JUCE reader.
  - (b) For MP3 sources, have the worker cache a decoded `original.wav` and use it for A/B.
    This costs disk.
  - (c) Use a gapless-aware C++ MP3 decoder. That is a new dependency.
- Tagless or odd MP3s decode 1105 samples late in both decoders, so they should agree unless
  JUCE handles priming differently. Verify this.

## BPM analysis

`spikes/python/bpm_compare.py` uses synthetic material:

- **Patterns:** four-on-the-floor, backbeat, half-time and a full pseudo-song.
- **Tempos:** 70/90/120/128/140/174 BPM.
- **Clips:** 30 s at 44.1 kHz with ±4 ms timing jitter.
- **Scoring:** Acc1 is ±4 % of nominal. Acc2 is ±4 % of nominal × {1, 2, ½, 3, ⅓}.
- librosa ran in a throwaway overlay (`uv run --with librosa==1.0.0`). The worker lock was not
  touched, and the overlay was removed from the uv cache afterwards.

| Estimator | Acc1 | Acc2 | Precision | Warm time / 30 s | Cold (new process: import + first call) | Extra install | Licence | Confidence |
|---|---|---|---|---|---|---|---|---|
| **In-house** (spectral-flux onsets → global ACF comb salience × log-normal prior at 120 BPM → long-lag refinement) | 16/24 | **24/24** | **±0.01 BPM** (e.g. 128.00, 140.01, 89.99) | **0.09 s** | **0.1 to 0.2 s** | **none** (numpy/scipy) | MIT (SNDS) | **yes**: `confidence` 0 to 1, plus half/double relative salience |
| librosa 1.0.0 `feature.tempo` | 15/24 | 24/24 | tempogram-bin quantized (128 → 129.2, 140 → 139.67, 90 → 90.67) | 0.16 s | 1.5 s (numba JIT) | about 174 MB, 20 packages (numba, llvmlite, scikit-learn, joblib, pooch, soxr (LGPL), msgpack, …); numba caps numpy < 2.6 | ISC | no |
| librosa 1.0.0 `beat.beat_track` | 14/24 | 24/24 | same | 0.17 s | 2.6 s | same | ISC | no |

Every miss is an octave error for all three estimators:

- 70 BPM is reported as about 140, driven by eighth-note hats.
- 174 BPM is reported as about 87.
- librosa also read 90 as 178, and one 140 as 70.

Candidates rejected without deep testing, because they have no Windows cp312 wheel or would
destabilize torch:

- madmom 0.16.1: 2018 sdist; its models are CC BY-NC-SA.
- aubio 0.4.9: 2019 sdist, GPL-3.
- essentia: no Windows wheels, AGPL-3.
- tempocnn: TensorFlow, AGPL.
- deeprhythm: needs torchaudio, nnAudio and librosa.
- beat-this 1.1.0: MIT and state of the art, but needs torchaudio, which caps torch at 2.11,
  plus a second checkpoint.

**Decision: `unknown-bpm-dependency` = in-house numpy/scipy estimator, no new dependency.**

- It is at least as accurate as librosa here and 100× more precise, which matters for the
  tempo-synced delay.
- Cold start is 10× faster, which matters for a short-lived worker.
- It adds zero install footprint, and it outputs confidence plus half/double salience that the
  metadata can store for correction UX.

Caveats: this was validated only on synthetic material, and the octave prior will make a
fixed choice for 70 and 174 BPM material. The planned numeric and half/double correction
covers this. Phase 2 should re-check it on the rights-cleared fixture and consider running it
on the separated `drums` stem. Keep an adapter seam so librosa (ISC) can be swapped in.

| # | Scenario | Result |

| 1 | Flushed child (`stdout.reconfigure(newline="\n", line_buffering=True)`, UTF-8, `ensure_ascii`) | 10 lines arrived **incrementally** (arrival spread 1.8 s over a 1.8 s run, delivery latency about 0 ms), LF only |
| 2 | Default Python stdout (no flush) | all 10 lines arrived **at exit** (1.8 s latency), and lines ended in **CRLF** |
| 3 | `{"type":"cancel"}` on stdin | child acknowledged (`cancelled`, reason `cancel_message`), exit code 4, 106 ms (one work step) |
| 4 | Parent closes stdin (EOF) | treated as cancel, exit code 4, 106 ms |
| 5 | `TerminateProcess` on the child only | child dead, **grandchild orphaned** (then cleaned up by the spike) |
| 6 | Child in a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then `TerminateJobObject` | child **and** grandchild dead, about 2 ms |
| 7 | Intermediate "app" process owning the job is killed (simulated app crash) | kernel closed the job handle, and the whole worker tree died |
| 8 | Hung worker ignores cancel | escalated to job kill after a 1 s grace period, dead in 1.01 s |
| 9 | Worker floods 2 MB to stderr while the parent does not read stderr | **child blocked** with 0 progress lines (pipe deadlock). With a draining thread it completed |

After the run no `python.exe` processes remained.

**Decision: `unknown-worker-channel` = newline-delimited JSON over stdout, control messages on
stdin, stderr for logs only.** No file or status channel is needed.

Worker requirements (Phase 2):

- Reconfigure stdout to UTF-8 with `newline="\n"` and flush every line. Also launch with
  `-u -X utf8` or `PYTHONUNBUFFERED=1 PYTHONUTF8=1`.
- Only protocol JSON may go to stdout. Keep `progress=False` in demucs.
- Treat stdin EOF as cancel.
- Map cancellation to demucs 4.1.0's `callback` (raise, then exit with the cancelled code).
  Cooperative cancel latency is at most one segment: about 2.4 s on this 4-core CPU and about
  0.2 s on CUDA.

What the C++ worker client must do:

- **Do not use `juce::ChildProcess` for the worker.** It can only read the child's output (no
  stdin write, so no cooperative cancel). Its `kill()` calls `TerminateProcess` on the direct
  child only, which is the orphan case in scenario 5. Confirm this against the pinned JUCE
  revision.
- Use a small Win32 wrapper:
  - `CreateProcessW` with `CREATE_SUSPENDED | CREATE_NO_WINDOW` and three anonymous pipes.
  - Use `STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` so only those pipe handles
    are inherited.
  - `AssignProcessToJobObject` to a job with `KILL_ON_JOB_CLOSE`, then `ResumeThread`. Creating
    suspended closes the race where the child could spawn processes before it joins the job.
  - Launch `worker\.venv\Scripts\python.exe -u -X utf8 -m snds_worker ...` directly (no
    activation).
- Keep the job handle open for the job's lifetime. If the app crashes, the kernel kills the
  worker tree (scenario 7).
- Run two reader threads:
  - stdout: split on `\n`, strip a trailing `\r` defensively, parse one JSON object per line,
    and report malformed lines as protocol errors.
  - stderr: drain continuously into the rotating worker log. Never leave it unread
    (scenario 9).
- Cancel sequence:
  1. Write `{"type":"cancel"}\n` and close stdin.
  2. Wait a grace period (suggested 5 s).
  3. `TerminateJobObject`.
  4. Remove the temporary job directory and keep the logs.
- Exit codes used by the spikes, as input to `define-worker-schema`: 0 ok, 1 failed, 3 CUDA
  failed (retry on CPU), 4 cancelled.

## OpenGL tier

Probe: `spikes/cpp/gl_probe` (`snds_gl_probe --force=none|context|version|shader
--paint-engine=default|software|direct2d --json=<file>`), run from the Release build while a
60 Hz `juce::Timer` measures message-thread gaps.

- **Observed:** despite the Microsoft Remote Display Adapter, the context is hardware:
  `NVIDIA Corporation`, `NVIDIA GeForce RTX 3060/PCIe/SSE2`, `3.2.0 NVIDIA 576.80`, GLSL
  `1.50 NVIDIA via Cg compiler`. The GLSL effect ran at about 55-58 fps.
- **Minimum tier (`unknown-opengl-minimum`):** OpenGL 3.2 core profile with GLSL 1.50 on a
  hardware renderer. Software renderers (GDI Generic, llvmpipe, SwiftShader, WARP) are
  classified as unsupported and go to the CPU fallback. The GDI Generic case could not occur on
  this machine; it is covered by unit tests of the classifier.
- **Fallback behaviour:**

| Forced failure | Fallback | Detach time | Steady timer gap, software paint | Steady timer gap, Direct2D paint |
|---|---|---|---|---|
| none | stays on GL | - | ~18 ms | ~18 ms |
| context never created (2.5 s watchdog) | yes | 0 ms | ~19 ms | ~96 ms |
| version too low | yes | 8-11 ms | ~19 ms | ~99 ms |
| shader compile failure | yes, driver log captured | 11-35 ms | ~19 ms | ~96 ms |

- **Findings for Phase 5:** detaching the context is fast and does not stall the timer, so the
  `OpenGLContext` lifecycle is safe for the message thread. Creating the context stalls the
  message thread once for 110-350 ms at startup. In this remote session the Direct2D renderer
  blocks each full-window repaint for about 100 ms, so the CPU fallback must rate-limit its
  repaints and/or prefer the software renderer when presents are slow.
